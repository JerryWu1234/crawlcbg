# Isolated RFB recording workspace with ephemeral Chromium state

This follow-up removes the recording-specific JPEG preview path, moves Chromium profile/cache state to bounded tmpfs, and replaces the preview UI with a token-bound noVNC workspace backed by a Fastify WebSocket↔TCP bridge. Awaited route-leave cleanup, coordinator rollback tests, pagination compiler journeys, and an explicit deterministic-RFB-versus-Docker boundary address most concerns from the first pass. Recording ownership still depends on receiving the start envelope, however, and the selected page is still identified only by index plus URL.

Watch for: **[P1, confirmed]** a lost committed start response or failed teardown stop can leave the recording and browser lease active; **[P1, confirmed]** a different CDP target with the same URL passes the clicked-target checks; **[P2, confirmed]** the privacy canary scan omits the managed Chrome profile and process output while documentation calls it non-persistence; **[P2, confirmed]** pagination Cypress proves compiler transitions but not Vue Flow parent containment.

**Verdict**: NEEDS_CHANGES

## High-level view

The recording JPEG chain is absent from the final tree: recorder screenshot methods, coordinator delegation, route, and preview component are gone, with route and Cypress assertions pinning the old endpoint to 404. The Compose default mounts both `/home/browser/profile` and `/tmp/chromium-cache` as bounded tmpfs; no named profile volume remains.

The workspace route preserves the clicked URL in history state, re-reads tabs, fails closed on index/URL drift, and waits for in-flight start and stop requests before normal Vue Router navigation. **[P1, confirmed]** Scope disposal still has only a response-supplied recording ID and a one-shot best-effort stop, so a lost response or failed teardown request has no server-side owner expiry or client-known ID to reclaim the lease.

**[P1, confirmed]** URL equality is not browser-target identity. `/api/tabs`, `BrowserTab`, the workspace handoff, and `RecordingCoordinator.start` carry only index and URL even though the Stagehand page exposes a stable CDP target ID, leaving close-and-replace and duplicate same-URL targets indistinguishable.

The live-view bridge now has bounded bidirectional flow control, high/low watermarks, hard caps, and an accepted-but-silent upstream deadline. The noVNC client scopes renewal requests, connection watchdogs, callbacks, and reconnect timers to a connection generation.

Pagination Cypress generates loop code, dissolves the loop, regenerates, and verifies linear selector order and removal of pagination helpers. **[P2, confirmed]** Its graph assertion only reads `data-parent-node`, so it does not prove that draggable children move with or remain constrained by the Vue Flow parent.

The E2E README explicitly says the RFB fixture cannot prove Xvfb/Openbox/x11vnc/Chromium compatibility or Docker tmpfs lifetime and names a Linux/Docker smoke follow-up. **[P2, confirmed]** It still describes `window-stream.p0.cy.ts` as proving sensitive-value non-persistence although the scanner excludes the managed Chrome profile and captured child-process output.

### Recording ownership still begins after the start response

Normal navigation now waits through `RecordingWorkspaceView.vue:136-148` and `RecordingPanel.vue:351-356`. **[P1, confirmed]** `useRecording.ts:745-783` can compensate only after parsing an ID from the start response; if the server commits `RecordingCoordinator.start` but that response is lost, `requestJson` throws without an ID to stop. `useRecording.ts:1307-1346` also discards the result of a one-shot `bestEffortStop` during disposal, while the start route accepts only `{ tabIndex, expectedUrl }` at `recording-routes.ts:57-70` and coordinator records have no owner deadline or heartbeat.

```text
POST /api/recordings commits recorder + live-view grant + browser lease
                    |
                    +-- response lost / teardown stop fails
                                      |
                                      +-- no durable owner ID; lease remains active
```

The new tests cover delayed successful responses, not a dropped committed response, rejected keepalive stop, or hard unload. Allocate an idempotent client owner/request ID before start and allow stop-by-owner, or expire recordings through a server-side lease/heartbeat; then test dropped-response and failed-disposal recovery.

### Index and URL still permit same-URL target substitution

`tab-routes.ts:23-33` serializes only index, title, URL, and favicon; `automation.ts:1-6` mirrors that shape. `RecordingWorkspaceView.vue:52-78` and `recording-coordinator.ts:201-213` compare index and URL before recorder creation.

**[P1, confirmed]** A closed target replaced at the same index with the same URL—or two same-URL tabs with different login state—passes both checks and can record a page other than the one clicked. `target-selection.cy.ts` mutates the URL, so it proves only different-URL drift. Return `page.targetId()` from `/api/tabs`, carry it through route state and the start body, resolve by target ID, and add a same-URL replacement journey.

### Privacy canary scans less than the coverage label implies

**[P2, confirmed]** `p0-harness.ts:959-962` creates `caseRoot/chrome-profile`, but `privacySnapshot` at `p0-harness.ts:1426-1448` walks only `runtimeDir`; retained `OwnedProcess.output` is also excluded. `window-stream.p0.cy.ts:158-164` inserts the canary through a CDP task and checks only UI plus runtime artifacts, while `e2e/README.md:49` labels the result “sensitive-value non-persistence.”

Keep the accurate Docker disclaimer at `e2e/README.md:52-55`, but either narrow the line-49 claim to server runtime artifacts or scan the whole marker-protected case root and captured process output. Real Docker tmpfs lifetime, x11vnc key release, and Chromium pixels remain the documented Linux/Docker follow-up.

### Compiler restoration is covered; Vue Flow containment is not

`pagination-loop.cy.ts:125-171` verifies loop helpers, dissolves the loop, rejects those helpers in regenerated code, and checks entry→body→next order. **[P2, confirmed]** The nesting check at `pagination-loop.cy.ts:119-146` only asserts the component-authored `data-parent-node` attribute. `RecordingFlowGraph.vue:96-166` supplies `parentNode`, `extent: "parent"`, and that same attribute to draggable nodes, so Vue Flow can ignore containment while the test remains green. Drag the loop parent and assert children move with it, then drag a child against the boundary and assert containment.

Compose config parsing and entrypoint shell syntax also passed. A real image/container smoke was not run; the README identifies it as separate follow-up coverage.
