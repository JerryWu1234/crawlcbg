****# 独立最小化 Chrome 后台执行与断线恢复

这组改动为手动脚本执行增加默认可视、可选后台的双模式；后台模式在同一 Chrome Profile 中创建独立最小化窗口，并用服务端事件记录与前端 `localStorage` 支持 SSE 断线后的继续运行和恢复跟踪。第二轮核验确认，`Target.createTarget` 已等待返回后走单一路径清理，URL 与全局后台槽位会在创建前预留，已登记的后台 target/window 已从 Tabs、ensure、activate 和 scheduler 页池中过滤，后台终态也会等待已跟踪操作及窗口关闭。默认仍为 visible，scheduler 不请求后台模式，增量状态接口要求受信任的 localhost/127.0.0.1 Origin。剩余阻塞集中在 facade 逃逸、跨窗口 popup 所有权和轮询乱序三处。

Watch for: **confirmed** (P1) Stagehand facade 可返回未受限 Page 并调用全局 Context 能力；**likely** (P1) 不同 `windowId` 的 popup 不会被过滤或关闭；**confirmed** (P1) 重叠轮询可在终态后重新写入 `isExecuting=true`；**confirmed** (P2) 新生命周期没有自动化回归覆盖。

**Verdict**: NEEDS_CHANGES

## High-level view

后台创建会复用控制页的 browser context，在导航前后确认新窗口最小化；取消落在 `Target.createTarget` 上时先取得 target id 再清理，终态由统一收尾延迟到窗口关闭验证之后。**likely** (P1)，所有权仍只记录初始 target 和单个 `windowId`，opener 派生的其他窗口不属于该 run。

SSE 断开不会 abort 后台任务，前端改按 sequence 增量轮询并可从 `localStorage` 恢复。**confirmed** (P1)，固定间隔允许请求重叠，而空增量响应返回后没有再次核对 run id，旧的 running 快照可以覆盖终态。

后台 page/Stagehand 使用拒绝列表 facade。**confirmed** (P1)，当前 Stagehand `V3Context` 的 `activePage()`、`awaitActivePage()`、`conn` 及全局 init-script/header/domain-policy/cookie 能力仍从代理穿出，因此它不是完整隔离边界。

visible 仍是参数弹窗的初始值，scheduler 不携带 `executionMode=background`；创建前 URL 锁与过滤页池保留了 scheduler 的可视执行路径。

### Stagehand capability facade 仍可回到原始浏览器上下文

`createBackgroundStagehandFacade` 只替换 `context.pages/newPage/close/setActivePage`，其余成员仍绑定到原始 `V3Context`；外层 abortable proxy 只增加取消，不重新施加后台限制（`apps/server/src/index.ts:312-337`）。当前依赖公开的 `activePage()` 和 `awaitActivePage()` 会返回原始 `Page`，后台脚本随后可调用未包装的 `close()` 或任意 `sendCDP()`，包括 `Page.bringToFront`。未拦截的全局 init-script/header/domain-policy/cookie API 会影响同 Profile 的可视页签，公开的 `context.conn` 也能完全绕过 Target/Browser CDP 拒绝列表。

这是 **confirmed** (P1)：逃逸接口来自当前安装版本的公开声明和实现。后台接口应改成 capability allowlist，只暴露限定到 owned page 的操作；不能把原始 Stagehand/Context 方法绑定回真实实例。

### 初始 windowId 不是完整的 run 所有权边界

服务端只登记 root target id 与一次 `onWindowReady(windowId)`，页池过滤和关闭验证都只匹配该窗口（`apps/server/src/index.ts:67-84, 1958-1965`；`apps/server/src/minimized-browser-window.ts:127-180`）。普通页面交互仍可通过带 features 的 `window.open`、OAuth/支付流程或 popup 点击产生另一个 Chrome window。不同 `windowId` 的 target 不会进入过滤集合，会出现在 Tabs/ensure/activate/scheduler 页池，收尾也不会关闭它。

这是 **likely** (P1)：代码确认所有权止于一个 window id，而 Chrome popup 可形成独立窗口。run 应按 opener lineage/target-created 事件认领派生 target 和窗口；收尾应循环到所有 owned targets/windows 达到固定点。

### 空增量旧响应会复活已结束的前端执行

`startExecutionStatusPolling` 立即请求一次，再用 `setInterval` 每秒继续请求；`refreshBackgroundExecution` 只在请求前核对 `activeExecutionId`，响应后仅在遍历 events 时复核（`apps/website/src/views/TabsView.vue:647-689`）。旧响应若 `events=[]`，会直接写入 `isExecutionStreamAccepted=true` 和 running 状态。

```text
poll A: running / events=[] ───────────────────┐
poll B: terminal ──> finishExecution()         │
                    runId=null, executing=false│
旧 poll A 晚到 ────────────────────────────────> executing=true
```

这是 **confirmed** (P1)：请求超过轮询间隔或响应乱序时，状态会变成“无 activeExecutionId、但 hasActiveExecution=true”，从而阻止新任务且无法取消。应串行轮询或取消旧请求，并在每个 `await` 后、任何状态写入前比较 run id/请求代次；终态应使该 run 的所有在途响应失效。

### 关键生命周期缺少可重复验证

本次差异没有新增测试，仓库测试也没有命中窗口 helper、background record 或断线恢复。`git diff --check HEAD` 通过；按只读要求未运行服务、浏览器、构建或可能写入格式化结果的 `vp check`。

这是 **confirmed** (P2)。需要 fake-CDP 的窗口生命周期单元测试、可控 deferred fetch/EventSource 的前端状态测试，以及覆盖同 Profile、最小化与派生窗口所有权的最小 Chrome 集成验证。
